# خطة التنفيذ — مواءمة المنصّة مع ميزات Open edX

> **المبدأ الحاكم:** العقد أولاً (Contract-first). لكل دفعة، يُحدَّد عقد الـ API ومخطط البيانات **قبل** أي كتابة، لمنع انحراف الواجهة عن الخلفية.
> **مصدر الحقيقة للحالة:** `docs/feature-matrix.csv`. **التحليل:** `docs/gap-analysis.md`.
> **التقدّم الحيّ:** `docs/PROGRESS.md` (يُحدَّث بعد كل دفعة).

-----

## 0. القواعد العامة

### تسلسل كل دفعة (إلزامي)
```
architect (يحدّد العقد + مخطط البيانات)
  → backend-dev + frontend-dev (ينفّذان وفق العقد)
    → integrator (يثبّت تطابق العقد طرفاً لطرف)
      → qa-tester (يكتب ويشغّل الاختبارات)
        → compliance (WCAG 2.2 AA + PDPL + RTL/عربية + SEO)
          → reviewer (البوّابة — لا اعتماد قبل توقيعه)
```

### تعريف الإنجاز العام (Definition of Done)
دفعةٌ «منجَزة» فقط إذا تحقّق **كل** ما يلي:
1. عقد الـ API موثّق ومطبَّق كما هو في الخلفية والأمامية (لا انحراف).
2. الهجرات تعمل وتتراجع نظيفاً؛ فهارس مناسبة؛ قيود سلامة مرجعية.
3. الصلاحيات (Policies/Gates/permissions) مطبَّقة ومختبَرة.
4. اختبارات Pest (وحدة + Feature) تغطّي المسار السعيد والأخطاء والصلاحيات — وتنجح.
5. اختبارات الواجهة (Vitest) للحالات: تحميل/خطأ/فراغ/نجاح — وتنجح.
6. `./vendor/bin/pint --test` و`npm run lint` و`npm run typecheck` نظيفة.
7. العربية وRTL وخط Tajawal سليمة؛ سمات a11y مضافة؛ لا أسرار في الكود.
8. تحديث `feature-matrix.csv` (الحالة + حالة الاختبار + توقيع المراجع) و`PROGRESS.md`.
9. توقيع **reviewer** صريح في المصفوفة.

### حواجز الجودة (تُشغَّل بعد كل دفعة)
```bash
./vendor/bin/pint --test
php artisan migrate:fresh --seed && ./vendor/bin/pest
cd frontend && npm run lint && npm run typecheck && npm test && npm run build
```

## 1. ترتيب المراحل (بالتبعيات والقيمة)

التسلسل يقدّم الامتثال (التزام قانوني) ثم الاكتشاف (SEO/a11y) ثم أدوات المعلّم ثم إثراء التعلّم ثم عمق التأليف. كل مرحلة شريحة رأسية قابلة للاختبار، وتتوقّف عند حدّها لعرض تقرير المراجع وأخذ موافقة صاحب المشروع.

| المرحلة | العنوان | الأولوية | لماذا الآن (التبعية) |
|---|---|---|---|
| A | الامتثال والهوية (PDPL/تفعيل البريد) | P0/P1 | التزام قانوني؛ أساس لبقية حقوق المستخدم |
| B | الاكتشاف والوصول (SEO + WCAG 2.2 AA) | P1 | أضعف جوانب Open edX؛ فرصة تفوّق؛ مستقلّ |
| C | أدوات المعلّم (Gradebook/مراجعة/بريد/إعلانات) | P1/P2 | يعتمد على بيانات الدرجات القائمة |
| D | إثراء التعلّم (Bookmarks/منتدى/ملخّصات/نص/فيديو) | P2 | تحسينات تجربة مستقلّة |
| E | عمق التأليف (متطلّبات/جدولة/تأليف جماعي/أنواع أسئلة/مكتبات) | P2 | الأثقل؛ يبني على عقود سابقة |

## 2. المرحلة A — الامتثال والهوية

**الهدف:** استكمال حقوق المستخدم تحت PDPL/GDPR وتأمين التسجيل.

### دفعة A1 — تفعيل البريد الإلكتروني
- **العقد (architect):** `POST /api/v1/auth/register` يُنشئ حساباً غير مفعّل؛ `POST /api/v1/auth/email/verify/{id}/{hash}` (موقّع) للتفعيل؛ `POST /api/v1/auth/email/resend`. الاستجابة قبل التفعيل: `403 email_unverified`.
- **البيانات:** استخدام `email_verified_at` القائم؛ تفعيل `MustVerifyEmail` على `User`.
- **الخلفية:** حدث `Registered` + إشعار تحقّق عبر قناة البريد القائمة (يحترم التفضيلات).
- **الأمامية:** شاشة «تحقّق من بريدك» + حالة إعادة الإرسال + معالجة الخطأ.
- **معيار القبول:** لا توكن فعّال قبل التحقّق؛ اختبار Feature يثبت الحجب ثم النجاح بعد التفعيل.

### دفعة A2 — الخدمة الذاتية للحساب
- **العقد:** `PATCH /api/v1/profile/account` (locale/timezone)، `PUT /api/v1/profile/password` (كلمة حالية + جديدة)، `GET /api/v1/profile/export` (تصدير بيانات JSON)، `DELETE /api/v1/profile` (حذف/إخفاء هوية ذاتي مؤكَّد).
- **البيانات:** لا جداول جديدة؛ إخفاء الهوية يعتمد soft-delete + تعمية الحقول الشخصية.
- **الأمامية:** صفحة «إعدادات الحساب» (RTL) بأقسام: اللغة/المنطقة، كلمة المرور، الخصوصية (تصدير/حذف).
- **معيار القبول:** تغيير كلمة المرور يبطل التوكنات الأخرى؛ التصدير يشمل بيانات المستخدم؛ الحذف يخفي الهوية ويحافظ على سلامة السجلات المالية/التدقيق.

### دفعة A3 — Retirement وإخفاء الهوية الإداري (PDPL)
- **العقد:** `POST /api/v1/admin/users/{id}/retire` (صلاحية `users.manage`) — إخفاء هوية مؤرشَف + سجل تدقيق.
- **معيار القبول:** بعد Retirement لا تظهر بيانات شخصية في أي استعلام؛ تُحفظ المراجع المجهّلة؛ موثّق في سجل التدقيق.
- **compliance:** يوثّق المسار في ملاحظة PDPL ويتحقّق من الاحتفاظ والتقليل.

**معالم/تعريف إنجاز المرحلة A:** المسارات الثلاث مختبَرة؛ لا تسريب بيانات بعد الحذف؛ توقيع المراجع. **توقّف لأخذ الموافقة.**

## 3. المرحلة B — الاكتشاف والوصول

**الهدف:** رفع محوري SEO وa11y فوق مستوى Open edX المرجعي. (واجهة فقط غالباً — منخفضة المخاطرة.)

### دفعة B1 — SEO الهيكلي
- **العقد:** لا تغيير خلفي جوهري؛ تُستهلَك حقول المقرر/المسار القائمة (title/summary/cover/slug/price). يحدّد architect شكل JSON-LD (`Course`, `Offer`/`CourseInstance`) ووسوم OG/Twitter وcanonical.
- **الأمامية:** `generateMetadata` لكل صفحة مقرر/مسار/شهادة + حقن JSON-LD عبر SSR + canonical + OG/Twitter.
- **معيار القبول:** صفحة مقرر تجتاز Google Rich Results (Course)؛ وسوم OG كاملة؛ canonical موحّد؛ اختبار Vitest يتحقّق من وجود الوسوم في DOM المُصيَّر.

### دفعة B2 — الوصول WCAG 2.2 AA
- **العقد:** قائمة تحقّق a11y (أدوار ARIA، تسميات، مناطق حيّة، تباين، focus، تنقّل لوحة مفاتيح، تخطّي للمحتوى).
- **الأمامية:** تمرير المكوّنات الأساسية (التنقّل، النماذج، المشغّل، الجداول) على القائمة.
- **qa-tester:** إدماج فحص a11y آلي (مثل axe في Vitest/jsdom) على الصفحات الرئيسة.
- **معيار القبول:** صفر مخالفات حرجة في الفحص الآلي؛ تباين AA؛ تشغيل المسارات الأساسية بلوحة المفاتيح.

### دفعة B3 — i18n/hreflang (اختياري ضمن المرحلة)
- hreflang + استكمال قاموس الترجمة. **معيار القبول:** وسوم hreflang صحيحة للنسختين.

**تعريف إنجاز المرحلة B:** SEO وa11y مختبَران آلياً؛ توقيع compliance + reviewer. **توقّف لأخذ الموافقة.**

## 4. المرحلة C — أدوات المعلّم

**الهدف:** سدّ فجوة لوحة المعلّم الحقيقية (الموجود اليوم للطالب فقط أو API فقط).

- **دفعة C1 — Gradebook للمعلّم:** `GET /api/v1/courses/{course}/gradebook` (صلاحية طاقم المقرر) يعيد مصفوفة طلاب×عناصر تقييم. أمامية: جدول درجات قابل للفرز/التصدير. قبول: المعلّم يرى درجات كل الطلاب؛ منع وصول غير الطاقم.
- **دفعة C2 — مراجعة التسليمات:** واجهة معلّم لعرض/تصحيح تسليمات الواجبات (تستهلك API القائم) + تجاوز/إعادة درجة. قبول: مسار تصحيح كامل من الواجهة مع تدقيق.
- **دفعة C3 — البريد الجماعي والإعلانات:** `POST /api/v1/courses/{course}/announcements` و`POST /api/v1/courses/{course}/bulk-email` (عبر الطوابير، تحترم التفضيلات). قبول: إرسال مُطابور موثّق؛ يحترم opt-out؛ مختبَر.

**تعريف الإنجاز:** كل دفعة مختبَرة بصلاحياتها؛ توقيع المراجع. **توقّف لأخذ الموافقة.**

-----

## 5. المرحلة D — إثراء التعلّم

- **دفعة D1 — العلامات المرجعية:** `GET/POST/DELETE /api/v1/bookmarks` + صفحة مخصّصة. هجرة `bookmarks`.
- **دفعة D2 — المنتدى (تمييز إجابة + متابعة):** `POST /threads/{id}/accept` و`POST /threads/{id}/subscribe`. حقول على `forum_posts`/جدول اشتراك.
- **دفعة D3 — ملخّصات الإشعارات:** أمر مجدول (Horizon) يجمّع نشاطاً يومياً/أسبوعياً حسب التفضيل.
- **دفعة D4 — البحث في النص + ضوابط المشغّل:** نص قابل للبحث/النقر الزمني؛ ضوابط سرعة/جودة/استئناف ظاهرة.

**تعريف الإنجاز:** كل دفعة شريحة مكتملة مختبَرة؛ توقيع المراجع.

-----

## 6. المرحلة E — عمق التأليف

- **دفعة E1 — المتطلّبات السابقة + امتحان الدخول:** قيد التحاق مشروط بإكمال متطلّب.
- **دفعة E2 — جدولة الإصدار والظهور:** تواريخ ظهور لكل قسم/درس.
- **دفعة E3 — التأليف الجماعي:** فريق مقرر بأدوار (RBAC على مستوى المقرر).
- **دفعة E4 — أنواع أسئلة إضافية:** dropdown، رقمي بهامش خطأ، فصل متعدّد الإجابات، (ثم Math/Drag&Drop عند الطلب).
- **دفعة E5 — مكتبات المحتوى:** بنك أسئلة قابل لإعادة الاستخدام عبر المقررات.

**تعريف الإنجاز:** كل دفعة مختبَرة؛ توقيع المراجع.

## 8. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| انحراف العقد بين الأمامية والخلفية | architect يثبّت العقد أولاً؛ integrator يتحقّق طرفاً لطرف قبل QA |
| كسر الامتثال (PDPL) عند الحذف | compliance يراجع كل دفعة تمسّ بيانات شخصية؛ اختبار «لا تسريب بعد الحذف» |
| تراجع في RTL/عربية | compliance يفحص كل واجهة جديدة؛ Tajawal وdir موروثان من التخطيط |
| تضخّم النطاق | reviewer يفرض انضباط النطاق: لا عمل خارج المصفوفة |
| الحفاظ على خضرة CI | حواجز الجودة تُشغَّل محلياً قبل كل دفع؛ الدفع بدفعات صغيرة |

## 9. تتبّع التقدّم

بعد كل دفعة: تحديث `feature-matrix.csv` (الحالة/الاختبار/التوقيع) و`docs/PROGRESS.md` (ما أُنجز، النتائج، التالي)، ثم لا تقدّم قبل توقيع المراجع. توقّف عند حدود كل مرحلة لعرض تقرير المراجع وأخذ الموافقة.
