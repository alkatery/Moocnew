# وثيقة مواصفات منصة MOOC المتكاملة — الإصدار 2 (مُنقّح هندسياً)

> **حالة الوثيقة:** نسخة عمل موجَّهة لفريق برمجي محترف (Laravel + Next.js).
> **أبرز تعديل في هذا الإصدار:** الدفع وحدة **اختيارية قابلة للتفعيل من الإدارة** (Feature Flag)؛ المنصة تعمل بكامل وظائفها في الوضع المجاني، وتتحول إلى الوضع التجاري بضغطة إعداد دون إعادة بناء. كما عُولجت الثغرات المعمارية والقانونية والتشغيلية الجوهرية، وأُضيفت **خطة تنفيذ مرحلية** بدل البناء الدفعي الشامل.

-----

## 0. فلسفة البناء (Build Philosophy)

1. **Modular Monolith وليس Microservices:** نبني نواةً واحدة منظَّمة في سياقات محدودة (Bounded Contexts) داخل Laravel، مع فصل صارم بين الطبقات (Domain / Application / Infrastructure). الانتقال إلى الخدمات الموزّعة قرار يُؤجَّل حتى يفرضه الحِمل الفعلي.
1. **شريحة رأسية رفيعة أولاً (Thin Vertical Slice):** نطلق MVP يعمل من طرفه إلى طرفه (تسجيل ← كتالوج ← التحاق ← دراسة ← شهادة)، ثم نضيف الطبقات. لا نبني كل الوحدات دفعةً واحدة.
1. **التجارة وحدة معزولة خلف Feature Flag:** كل ما يتعلق بالمال (الطلبات، الدفع، الفواتير، دفتر الأستاذ، السحوبات) يعيش في سياق `Commerce` مستقل، يُفعَّل أو يُعطَّل من إعداد إداري واحد. الالتحاق لا يعتمد على الدفع، بل الدفع **بوابة شرطية** قد تكون مُفعَّلة أو لا.
1. **القرارات المعمارية الكبرى تُحسم قبل أول سطر:** تعدد المستأجرين، المصادقة، بناء الفيديو أم شراؤه، وبوابات الدفع — تُحسم في وثيقة قرارات معمارية (ADR) قبل التطوير.

-----

## 1. وضعا التشغيل: المجاني والمدفوع (Operating Modes)

هذا هو المحور الذي يحكم تصميم الالتحاق والكتالوج والإحصاء.

### الإعداد المركزي

- إعداد عام `payments.enabled` (Boolean) يتحكم به **Super Admin** من لوحة الإعدادات، ويُخزَّن في جدول `settings` ويُكاش في Redis.
- لكل دورة حقلان: `pricing_type` ∈ (`free`, `one_time`, `subscription`) و`price_minor` (المبلغ بوحدات صحيحة — هللات/سنتات، **لا تُخزَّن النقود كـ float إطلاقاً**).

### منطق الالتحاق المُوحَّد (`EnrollmentService`)

|الحالة                                                                 |السلوك                                                                                                                       |
|-----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
|`payments.enabled = false`                                             |كل الدورات تُعامَل كمجانية → التحاق مباشر، حالة `active` فوراً. تُخفى الأسعار والسلة والسحوبات والفواتير من الواجهة.             |
|`payments.enabled = true` و`pricing_type = free` (أو `price_minor = 0`)|التحاق مباشر، حالة `active`.                                                                                                 |
|`payments.enabled = true` ودورة مدفوعة                                 |إنشاء `Order` بحالة `pending` ← تحويل لبوابة الدفع ← عند نجاح `webhook` يُفعَّل الالتحاق (`active`) **وتُصدَر فاتورة ZATCA** آلياً.|

### الأثر المعماري

- عند تعطيل الدفع: مسارات (Routes) وواجهات سياق `Commerce` لا تُسجَّل/تُخفى، ودفتر الأستاذ والسحوبات والفواتير غير نشطة، لكن الكود حاضر وجاهز للتفعيل دون أي إعادة نشر هيكلية.
- جدول `enrollments` لا يحمل أي اعتماد مباشر على `orders`؛ الربط يتم عبر `order_id` اختياري (`nullable`) يُملأ فقط في الوضع المدفوع.
- التقارير المالية والإحصاء التجاري تظهر فقط حين تكون التجارة مُفعَّلة.

## 3. القرارات المعمارية الكبرى (ADR — تُحسم أولاً)

1. **تعدد المستأجرين (Multi-tenancy):** هل المنصة مفردة (Single-tenant) أم منصة بيضاء (White-label) متعددة المستأجرين تخدم جهات/مشايخ متعددين؟ هذا قرار يحدد بنية قاعدة البيانات بالكامل (Schema/DB لكل مستأجر، أو `tenant_id` على كل جدول). **يجب حسمه قبل أي migration**؛ التحوّل لاحقاً مكلف جداً.
1. **بناء الفيديو أم شراؤه:** الموصى به في MVP: خدمة مُدارة (تشغيل موقّع + ABR + CDN). البناء الذاتي يدخل لاحقاً عند الحاجة لـ DRM متقدم أو لخفض الكلفة عند حجم كبير.
1. **استراتيجية المصادقة:** Sanctum للويب والجوال.
1. **قنوات الدفع:** اختيار المُجمِّع (Moyasar/Tap/HyperPay) وتغطيته لـ mada/Apple Pay/STC Pay، مع تصميم idempotency للـ webhooks منذ البداية.

## 4. نظام الأدوار والصلاحيات (RBAC)

يُبنى باستخدام `spatie/laravel-permission` لإدارة الأدوار، مع **Laravel Policies & Gates** للقرارات الدقيقة على مستوى الموارد.

1. **الإدارة العليا (Super Admin):** اطلاع كامل، إدارة الإعدادات (ومنها **مفتاح تفعيل الدفع**)، الشؤون المالية (في الوضع المدفوع)، الصلاحيات، الإحصاء الكلي، الدعم.
1. **المشرف (Supervisor):** مراجعة الدورات قبل النشر، متابعة المدرسين، إدارة نزاعات ساحات النقاش (أدوات إبلاغ/إخفاء/حظر)، مراقبة النشاط.
1. **المدرس (Instructor):** بناء الدورات، الاختبارات، التصحيح، التواصل، و**سحب الأرباح (في الوضع المدفوع فقط)**.
1. **الطالب (Student):** التسجيل، الالتحاق/الشراء، الدراسة، الاختبارات، الشهادات.
1. **الزائر (Visitor):** التصفح، التواصل، إنشاء حساب.

## 5. الوحدات الوظيفية (Bounded Contexts)

### أ. الهوية والملف الشخصي (Identity)

- بيانات: الاسم، البريد، كلمة المرور المُشفَّرة (bcrypt/argon2)، الهاتف الدولي، الدولة، المستوى التعليمي، الاهتمامات.
- ربط حسابات تواصل (X, LinkedIn, Facebook, Instagram) تظهر في صفحة المدرس التعريفية.
- موافقات PDPL: تسجيل موافقة المستخدم على سياسة الخصوصية والبيانات مع طابع زمني وإصدار السياسة.
- لوحة CMS لإدارة الواجهة (بنرات، دورات مميزة، "من نحن"، روابط التواصل العامة).

### ب. المنهج وإدارة الأصول (Curriculum & Asset Manager)

- الهيكلية: دورة ← أقسام ← دروس (فيديو، مقال، ملف، بث مباشر).
- رفع مركزي يدعم (PDF, DOCX, ZIP) بمسارات محمية: لا تنزيل إلا عبر **رابط موقّع مؤقت** للطالب المُلتحِق فقط.
- **خط الفيديو (مُفصَّل):** الرفع ← الترميز إلى جودات متعددة (ABR) عبر الخدمة المُدارة ← التشغيل عبر رابط موقّع/توكن قصير العمر ← منع التنزيل المباشر. حالة الفيديو تُتابع عبر `webhook` من خدمة الفيديو (`processing` → `ready`).

### ج. الالتحاق والوصول (Enrollment & Access) — **مفصول عن الدفع**

- دورة حياة الالتحاق (State Machine): `pending` → `active` → `completed` → (`expired` | `refunded`).
- صلاحية الوصول: دائمة أو محدودة بمدة (`access_expires_at`).
- تتبّع التقدم: إكمال كل درس، **موضع تشغيل الفيديو (resume position)**، نسبة الإنجاز.
- التحاق مباشر في الوضع المجاني؛ التحاق مشروط بالدفع في الوضع المدفوع (انظر §1).

### د. التجارة والدفع (Commerce) — **وحدة اختيارية خلف Feature Flag**

> تعمل هذه الوحدة بالكامل **فقط** عند `payments.enabled = true`. عند التعطيل تُخفى واجهاتها ولا تُسجَّل مساراتها.

- **الطلبات (Orders):** إنشاء طلب، حالات (`pending`/`paid`/`failed`/`refunded`)، **idempotency key** لمنع الازدواج.
- **الدفع:** تكامل مع المُجمِّع (mada/Apple Pay/STC Pay)، استقبال `webhooks` مع التحقق من التوقيع و**idempotency** صارم.
- **الكوبونات والخصومات:** نسبة/مبلغ، حد استخدام، تواريخ صلاحية.
- **الاشتراك مقابل الشراء المفرد:** دعم النموذجين عبر `pricing_type`.
- **دفتر الأستاذ المزدوج (Double-entry Ledger):** كل حركة مالية قيدان (مدين/دائن) — هو **العمود الفقري** لأرباح المدرسين والسحوبات والتسويات. لا يُبنى لاحقاً.
- **سحب الأرباح (Payouts):** محفظة مدرّس، حد أدنى للسحب، حالة طلب السحب، تسوية.
- **الاسترجاع (Refunds):** سياسة، نافذة زمنية، أثر على الالتحاق ودفتر الأستاذ.
- **فاتورة ZATCA:** إصدار فاتورة إلكترونية متوافقة آلياً عند الدفع الناجح (المرحلة المطبَّقة حسب تصنيف المنشأة).

### هـ. محرك الاختبارات والواجبات (Assessment Engine)

- أنواع الأسئلة: MCQ، صح/خطأ، إجابة قصيرة، مع **بنك أسئلة** ووقت محدد وخلط عشوائي.
- **منع الغش واقعياً:** بنك أسئلة + خلط ترتيب الأسئلة والخيارات + توقيت صارم + بصمة جهاز/IP + قيود على إعادة المحاولة. **`Browser Focus Tracking` ضعيف ويُتجاوز؛** الـ Proctoring الكامل (كاميرا/مراقبة) سياق مكلف وحسّاس قانونياً → **خارج MVP**.
- الواجبات: رفع ملف من الطالب، لوحة تصحيح للمدرس (ملاحظات + رصد درجة يدوي).

### و. الجدولة والفصول الحية والتذكيرات (Scheduling & Dispatcher)

- الفصول الحية: تكامل API مع Zoom/BigBlueButton، مع إدارة سعة المقاعد (Concurrency-safe).
- تقويم موحّد (FullCalendar) يدمج الفصول والاختبارات ومواعيد التسليم، **ودعم التقويم الهجري**.
- التذكيرات عبر **Laravel Task Scheduling + Queues**: تنبيهات قبل الحصة بـ 30 دقيقة وعند اقتراب التسليم، **مع مراعاة المنطقة الزمنية لكل مستخدم** ومعالجة الوظائف الفاشلة.

### ز. التواصل والدعم (Communication Hub)

- ساحات نقاش (Threaded) داخل كل دورة مع Mention وإشعار فوري و**أدوات إشراف** (إبلاغ/إخفاء/حظر/مكافحة سبام).
- نظام تذاكر (Ticketing) يربط الطالب بالمشرفين.
- نموذج تواصل للزوار موجَّه للإدارة/المبيعات.
- شات حي بين الطالب والمدرس: **مؤجَّل لمرحلة لاحقة** (تكلفة WebSocket/تشغيل).

### ح. الشهادات (Certificates)

- توليد PDF بقالب، **رقم تسلسلي فريد**، و**تحقق عام** عبر QR + رابط تحقق عام لمنع التزوير.

### ط. الإشعارات (Notifications)

- مبنية على Laravel Notifications: قنوات (Email/SMS/WhatsApp/Push)، **مركز تفضيلات للمستخدم**، وإدارة قوالب.

### ي. الرقابة والإحصاء (Monitoring & Analytics) — **مُراجَع لأجل PDPL**

- **الطلاب المتواجدون الآن:** عدّاد متصلين عبر Redis Heartbeat.
- **"ماذا يُدرَس الآن":** ميزة المراقبة الفردية اللحظية **مكلفة ومشكوك في مشروعيتها تحت PDPL** (معالجة بيانات سلوكية فردية). **التوصية:** الاكتفاء بإحصاء مُجمَّع (عدد المتواجدين، الدروس الأكثر مشاهدةً الآن) في MVP، وتأجيل/مراجعة المراقبة الفردية مع أساس نظامي وموافقة صريحة.
- **سجل النشاطات (Activity Logs):** تسجيل الأحداث المهمة مع طابع زمني (تجنّب تخزين IP إلا لضرورة أمنية وبسياسة احتفاظ محددة).
- **الإحصاء المتقدم:** نسب الإنجاز، **معدل التسرّب (أين يتوقف الطلاب؟)** عبر نهج أحداث (Event-based)، وإحصاء تجاري (المبيعات/النمو) **يظهر فقط في الوضع المدفوع**.

## 6. نموذج البيانات الأساسي (Core Data Model)

أبرز الجداول والمبادئ:

- `users`, `roles`, `permissions`, `model_has_roles`.
- `courses` (`pricing_type`, `price_minor`, `status`), `sections`, `lessons` (`type`, `asset_path`, `video_id`, `video_status`).
- `enrollments` (`user_id`, `course_id`, `status`, `access_expires_at`, `order_id` **nullable**, `progress_percent`).
- `lesson_progress` (`enrollment_id`, `lesson_id`, `completed_at`, `video_position`).
- `quizzes`, `questions`, `question_bank`, `quiz_attempts`, `assignments`, `assignment_submissions`.
- **(الوضع المدفوع فقط):** `orders`, `payments`, `coupons`, `ledger_entries` (دفتر أستاذ مزدوج), `instructor_wallets`, `payout_requests`, `invoices` (ZATCA).
- `notifications`, `notification_preferences`, `tickets`, `forum_threads`, `forum_posts`, `certificates`, `activity_logs`, `settings`.

**مبادئ ملزِمة:** النقود بوحدات صحيحة (`*_minor`)؛ `soft deletes` على الكيانات الحسّاسة؛ **سجل تدقيق (Audit Trail)**؛ فهارس (`Indexes`) على أعمدة الاستعلامات الإحصائية الكبيرة.

## 7. التعريب والامتثال (Localization & Compliance)

- **i18n:** بنية ترجمة كاملة للواجهة والمحتوى، **RTL** افتراضي، خط Tajawal.
- **البحث العربي:** عبر Meilisearch/Typesense (أفضل من البحث النصي الخام).
- **التقويم الهجري:** في العرض والجدولة والتذكيرات.
- **PDPL:** أساس نظامي لمعالجة البيانات، موافقات مُسجَّلة، حق الوصول/الحذف، سياسة احتفاظ، وإقامة البيانات.
- **ZATCA (الوضع المدفوع):** فاتورة إلكترونية متوافقة، مع التزام المرحلة المطبَّقة على المنشأة.

## 8. المعايير الهندسية الصارمة (Engineering Standards)

1. **الأمان:** حماية من SQL Injection / XSS / CSRF؛ تشفير البيانات الحسّاسة؛ تشغيل فيديو موقّع/مشفّر؛ **idempotency** لكل عمليات الدفع والـ webhooks؛ Rate Limiting.
1. **الأداء:** Database Indexing للاستعلامات الثقيلة؛ Eager/Lazy Loading حسب الحاجة (تجنّب N+1)؛ معالجة الوسائط في الخلفية عبر Queues؛ استراتيجية كاش وإبطال واضحة.
1. **الجودة والاختبار:** **اختبارات آلية (Pest/PHPUnit)** تغطية وحدة + Feature؛ **CI/CD** (GitHub Actions)؛ بيئات `staging`/`production`.
1. **الرصد والتعافي:** Sentry/Flare لرصد الأخطاء؛ تسجيل مُهيكل؛ **نسخ احتياطي دوري وخطة تعافٍ (DR)**؛ مراقبة الطوابير عبر Horizon.
1. **التوثيق:** توثيق API عبر **OpenAPI/Swagger**؛ تعليقات على الوظائف المعقدة؛ سجلّ قرارات معمارية (ADR).
1. **تصميم API:** ترقيم إصدارات (`/api/v1`)؛ مصادقة Sanctum؛ Rate Limiting؛ استجابات أخطاء موحّدة.

## 9. رحلات المستخدم المصححة (User Journeys)

**الإدارة:** التهيئة ← **ضبط مفتاح تفعيل الدفع** ← (في الوضع المدفوع: ضبط بوابات الدفع وZATCA) ← التصنيفات ← اعتماد المدرسين ← مراقبة الأداء.

**المعلم:** الطلب ← الموافقة ← بناء المنهج ← رفع الفيديو/الملفات ← جدولة الفصول ← التفاعل ← رصد الدرجات ← (الوضع المدفوع: سحب الأرباح).

**الطالب — مسار مزدوج:**

- *وضع مجاني:* تصفح ← التحاق مباشر ← دراسة ← اختبار ← تقييم ← شهادة.
- *وضع مدفوع:* تصفح ← طلب/دفع (mada/Apple Pay) ← تفعيل التحاق + فاتورة ZATCA ← دراسة ← اختبار ← تقييم ← شهادة.

-----

## 10. خطة التنفيذ المرحلية (Phased Delivery)

### المرحلة 0 — قرارات وتأسيس

حسم الـ ADR (tenancy، auth، فيديو، دفع) ← هيكلة المشروع والسياقات ← CI/CD وبيئات ← Sandbox.

### المرحلة 1 — MVP (شريحة رأسية كاملة)

الهوية والصلاحيات ← الكتالوج + البحث ← **الالتحاق (وضع مجاني فقط مفعّل ابتداءً)** ← مشغّل فيديو بوصول موقّع ← تتبّع التقدم ← الاختبارات الأساسية ← الشهادات + التحقق ← الإشعارات (Email/SMS) ← لوحة إحصاء مُجمَّع ← اختبارات ورصد.

### المرحلة 2 — تفعيل التجارة + توسعة

وحدة `Commerce` كاملة خلف الـ Flag (الطلبات/الدفع/الكوبونات/دفتر الأستاذ/السحوبات/الاسترجاع) ← فاتورة ZATCA ← الفصول الحية والتقويم والتذكيرات ← ساحات النقاش والإشراف ← التذاكر.

### المرحلة 3 — تعميق

الشات الحي ← إحصاء متقدم (تسرّب/أحداث) ← WhatsApp/Push ← تطبيق جوال ← (عند الحِمل) خط فيديو ذاتي/DRM ومراجعة البنية للتوسع.

### مؤجَّل صراحةً حتى يثبت الطلب

Kubernetes، المراقبة الفردية اللحظية، الـ Proctoring الكامل، الشات الحي، الخدمات الموزّعة.

-----

### خاتمة

النواة الصحيحة للبناء: **الهوية والصلاحيات** أولاً، ثم **الكتالوج والالتحاق والدراسة** (تعمل مجاناً بالكامل)، وتبقى **التجارة وحدةً جاهزةً للتفعيل** متى قررت الإدارة ذلك — دون أي إعادة بناء. كل ما عدا ذلك يُضاف على مراحل قابلة للاختبار، مع حسم القرارات المعمارية الكبرى قبل كتابة أول سطر.
